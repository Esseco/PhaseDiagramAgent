# Relax+MC 阶段依赖提交策略

日期：2026-10-14

用户批准：阶段内多个 GPU 作业并行，全部结束后分析，再进入并行 MC；CPU 分区 p1。

实现：短 CPU 入口提交整阶段 GPU 分组作业，保存每个 sbatch --parsable 回执，再提交依赖所有 ID 的 afterany CPU 分析作业，然后退出。分析作业校验任务完成标记及结果校验和，应用已有反馈和凸包分析，核验通过后准备下一阶段、提交其 GPU 作业及依赖分析，再退出。Slurm 负责等待，无长期运行的总控、无完成计数抢锁触发器。GPU 并行仍按现有整阶段提交策略及已批准的分组计划执行，实际运行取决于调度资源。

CPU 入口及汇总默认 p1、1 核、8G、无 GPU；继承已有 Python 环境激活方式。可用 stage_profiles.relax_mc_cpu 显式覆盖 CPU 资源；含 GPU 申请的控制配置会被拒绝。资源配置纳入输入方案快照和校验和。每包最多一个入口加四个阶段分析作业，均执行后退出。

状态和容错：所有提交先记录意图、再记录回执；回执不确定时停止且保留记录，不盲目重提。阶段锁串行化控制入口，重复入口复用回执，过期阶段调用不推进。任一 Relax/MC 失败或缺少有效结果即暂停，不进入下一阶段、不自动补跑。正常结束、暂停或失败后发布原结果归档到同名 _output 文件夹。

文件交互保持 submit_all.sh、run_upload.py、inputs.zip 三文件，Python 只在分配的计算节点执行。旧回传接口和旧包仍可读取运行；新包使用 phase_dependencies 标记。未改其他单阶段提交工作流。未改现有 Co、Cr 在超算上执行的包，未触碰科学项目状态、结构、模型、预算与结果。未运行真实 Slurm 或计算，未启动、停止或重启项目服务。

验证：暂存代码完整假 Slurm 回归 6 passed，包含 Relax+三段 MC、全阶段依赖 ID、重复/过期调用、失败/缺失结果、未知回执；生产源码提交/CPU配置/最终输出/紧凑交互回归 9 passed；生产提交意图检查 1 passed。生产输入完整清单和 CPU 入口回归 1 passed（34.09 秒）。完整流程测试因 Windows 文件处理较慢耗时 363.80 秒，没有调用真实计算。新测试的 importlib 辅助模块加载以及旧 GPU 总控断言已修正。

生产源码哈希部署前逐一核对，原件位于工作区 build/slurm_phase_dependencies/baseline。最终部署文件均与暂存源码核对一致；workflow_reply_presentation 保留历史格式，仅改相关展示段落。部署后运行中的服务需用户手动重启才能加载新生成策略；已上传旧包不自动替换。
