# 交互阻塞与 LLM 用量检查

已更新生产源码 15 个文件；生产源码验证 187 项测试通过。没有启动、停止或重启真实服务，没有改动 Co/Cr/FeMn 的科学状态、审批、模型或计算进度，没有真实模型 API 调用或 HPC 提交。

## 原因与修复

- Co 先前的审批丢失已修复。本轮检查发现相同表象下还有其他流程问题，不能仅通过改提示词解决。
- Cr 的原始 448 个 Relax、29 个 MC 已完成，但模型没有明确看到第二轮现有规则的可分配范围。现有数据核算为 1 个分支、30 步。现在向模型提供与审批预览同源的只读分配事实；非法 MC 方案允许一次模型修订，之后重新审批，程序不替模型选择科研路线。
- 保存的快照在源码升级后可能仍命中旧指纹。现在实际科学模型调用边界也刷新执行事实，避免沿用旧缓存中的缺失条件。
- FeMn 的 285 个刷新任务已回收为失败，261 个单点和24个弛豫均找不到登记的微调模型文件。原先刷新状态仍为 waiting_results，展示层覆盖具体错误且失败任务不列入等待文件，造成“等待结果”的死循环。现在按任务终态显示失败计数和真实原因。
- 获批刷新重试改为跟踪新任务 ID；旧失败结果保留，新任务不继承旧 GPU 耗时和执行证据。
- 新提交包在派发任何子作业前统一检查模型文件及已登记的 SHA256/大小；本地可用权重只打包一份、使用相对路径。缺失依赖会停止派发，而非让整批 GPU 任务失败。旧提交收据保持防重，不能盲目重新提交旧任务。
- 收敛检查证据不足会明确说明缺少不同模型轮次记录、DFT误差验证等，并将上次检查结果交给模型，避免重复检查同一事实。
- 普通语义仍交给 LLM；没有增加关键词科学动作选择器，没有放宽批准/拒绝权限。

## LLM 用量与压缩

账本累计记录：Co 22 次调用、818937 输入/42760 输出 token；Cr 17 次、519626 输入/26909 输出；FeMn 92 次、7865400 输入/380110 输出。这些是历史累计的项目计数，不是本轮花费，也不等于每条消息都会调用模型。状态查询已有零模型调用路径；科学决策有必要上下文。

FeMn 近期单次常约7万输入 token，部分轮次出现对话契约修正与 API 响应重试。科学信息、覆盖、同份证据在引用目录中重复发送；对话修正还重发科学工具契约与候选，造成可避免的输入和思考成本。

现在保留所有科学候选/指标/版本和人工长期约束，用无损字典列编码压缩重复值；引用目录指向同一请求中已存在的证据；LLM 用量历史只发送累计摘要。advance 的未使用说明文字可省略，避免为该字段再调用模型；真正格式错误的对话只用小载荷修正一次，不带科学工具契约，不启用深度推理。

同份科学事实发送载荷的字符量：Co 88334→65750（25.6%）；Cr 95562→70017（26.7%）；FeMn 149828→107857（28.0%）。这是离线字符测量，不声称已发生的真实 API token 降幅；新请求的账本才反映实际 token。未截断科学候选以制造降幅。
