# Three scientific decision points

The Agent chooses branch sampling, DFT sampling and next-round direction. Code supplies versioned evidence, checks legality and runs existing modules. ScientificDecision records bottleneck, alternatives, expected outcome, success criterion and limitations; these are model statements, not verified facts. DFT purposes distinguish hull verification, model improvement, coverage and shared-bias checks.

Projects enable the contract with state.scientific_decision_policy.schema_version=1. Existing saved approvals remain unchanged; maintenance/recovery actions are not forced into scientific decision contracts. New LLM decisions receive one bounded formatting correction, then stop with an explicit error. No numeric gain or convergence result is supplied by LLM authority.

A new branch plan with a valid cost preview displays a narrow module_execution_scope. After generation, code diagnoses only the returned branch IDs and prepares Relax–MC input under the approved config/model/rules, at most three segments and the displayed cost envelope. This is one approved workflow, not an additional strategy decision. Exact diagnosis exceeding the envelope blocks packaging and preserves generated structures. Old generation proposals lacking the envelope retain their old behavior. Explicit stepwise preference disables this continuation.

DFT selection already prepares approved task inputs through the existing handler. Training, activation and model-refresh use the existing validation/approval gates: candidate identity, regression validation and exact refresh workload are only known later; this change does not grant unbounded activation or future refresh authority. They remain boundaries when the approved plan does not contain that exact scope.

Feedback correlates direct tasks, explicit child IDs, scientific parent task keys and package IDs; missing costs remain unknown. It does not attribute hull improvements to a strategy without measured, version-matching evidence.

Run the targeted tests with py1 and the configured Process_AL_MC backend. No real HPC jobs, services or model API calls are needed. Changes load on the user's next manual service start.
