# Reopening a completed model refresh

Status: the version-bound preview and reopen entry support ordinary completed refreshes and recovery cycles. Reopen preserves the previous attempt and hull, resets the new task scope and marks the publication not ready. Ordinary reopens bind compatible exact-frame results to the new plan. Preparation rechecks that evidence and creates inputs only for missing frames. Recovery verifies the reused results alongside new results, while new-attempt task IDs stay separate for extrapolation statistics. Input preparation and HPC upload/submission retain separate approvals. Cross-process end-to-end failure recovery still requires further verification.

A new refresh must preserve the completed refresh plan, task records, approval, data provenance and plots while preventing its result from being treated as the newly requested refresh. The existing refresh gate only handles active refreshes, and the existing extrapolation quarantine is tied to a proven extrapolation failure; neither is a general-purpose reopen operation.

Implement through an explicit Agent entry, using the project lifecycle lock and version-guarded transaction. Bind the requested project, active model, old refresh checksum, current hull version and trusted baseline. Reject pending or unsettled execution, stale evidence, conflicting calls and duplicate replay. Preserve the old completion and recovery evidence. Freeze a new plan through the current `refresh_preview` and D/H rules, with a distinct attempt identity. Keep old results available as historical evidence; reuse a result only when its exact input frame, active model, requested operation and required force/relaxation evidence satisfy the newly frozen plan. Otherwise identify it as needing new computation. Do not mix old and new attempt task IDs when calculating extrapolation failure fractions. Do not turn historical valid records into invalid scientific results merely because a previous hull publication was superseded.

The current publication must be marked superseded or replaced through the existing publication transaction, preserving referenced historical files and ensuring that `latest` cannot appear to be the new result while the rerun is pending. Reopen must never prepare inputs or submit HPC work. Apply the existing separate direction, input, upload and submission approval requirements.

Before applying to a real project, test synthetic projects for state and publication rollback, strong-version conflicts, exact-frame and model matching, completed versus unfinished tasks, old/new extrapolation scopes, repeated requests, crash/restart and concurrent Agent/Codex access. Verify compatibility with existing recovery cycles, model activation, and the generation gate. Real services must not be restarted automatically.
