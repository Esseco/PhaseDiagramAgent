# Codex 原生团队性能诊断与优化（2026-11-10）

## 结论边界

本记录针对 Codex 原生团队的本地处理路径：CodexTeam → LocalAgentControl 的只读上下文 → 证据/快照/角色投影 → 无损表格 → 响应编码。没有把普通项目 Agent 的模型调用或串行专家图当成本次运行路径。

已证实的根因是重复完整解析、快照物化及表格候选表示的重复复制/编码；重型本地工作处于锁内，同步 stdio 因此无法同时处理后续消息。锁本身在无竞争合成测量中等待很小。未发现足够证据把原生模型推理时间、长聊天继承、客户端缓冲或无限内存泄漏归因于上述代码。

源码已修改；没有部署、重启真实服务、调用真实模型决策、改写真实科研状态或操作 HPC。合成数据的结果不能说明真实 92–331 MB 项目已经解决。

## 运行中版本与只读真实定位

只读进程检查发现 14 个以 py1 启动、指向同一 NaNi 运行配置的 MCP 进程；两个工作集快照约为 2.03 GiB 和 0.99 GiB。这些是瞬时工作集，不是峰值或活动请求数。启动时间早于部分磁盘源码更新，命令使用 phase_agent.runtime.codex_mcp；没有可用的已加载模块 SHA 证明其代码版本，也未向这些进程注入检查或执行生命周期操作。不能把本次磁盘源码测量当作它们已加载的运行版本。

只读取运行配置中的状态路径、文件元数据、小型字段索引及最近三个团队文件的计数。观测到 NaNi state.json 为 337151700 bytes，索引中 tasks 约 77.5 MB、event_history 约 57.4 MB、action_records 约 30.7 MB、decisions 约 28.1 MB、invocations 约 23.7 MB。索引这里只作规模线索，不作为科学事实或授权。没有完整解析或复制该真实状态。

26 个团队记录中最近三个：当前咨询尚无意见，另两个已提交讨论各有两条专家意见，末尾事件为意见、草案、Simulation 计划、人工接受；该有限样本没有证明同一 revision 重复咨询。无法从这些记录核实原生客户端是否继承长聊天、是否重复派发或等待模型，相关假设未当作结论。

## 实现改动

- codex_team.py 复用既有 IndexedState，只解析消费者实际访问的字段。旧格式、失效/损坏索引、不兼容 Mapping 访问及尚未转移的初始状态保留完整读取回退。完整索引内容核验和前后强 state/control 身份校验均保留；没有靠只看 mtime 代替一致性。
- 字段和缺失字段只在本次调用内复用，避免反复元数据访问；缓存容量为本次访问的根字段/键，随调用释放。没有新增跨请求完整状态缓存、四份记忆或上下文管理 Agent。原有控制层摘要缓存不改。
- start 的前置审批/训练交接检查复用同一状态读取；advise、内联计划草案及 simulate 的校验和视图复用同一快照。
- snapshot.py 使用一次 JSON 树分离、分字段 C 编码计算原规范哈希，去掉常规路径的整串 JSON 再解析。非字符串历史字典键保留原完整编码回退。角色先排除已证明相等的重复项，再复制；True/1/1.0 和有符号零不合并。保留独立任务包、全部相关科学数值、未知风险和角色权限。
- transport_tables.py 每列复用规范值编码和大小计算，只在需要时分配行单元数组；不再为多个候选深复制整份嵌套证据，比较前释放大列的编码查找。所有行、数值、JSON 类型、路径前缀和分组顺序仍可无损还原。
- phase_team_advise 新增 compact，MCP 默认 true，返回绑定 team_id/revision/snapshot_id 的确认及 remaining_roles；Python 方法默认仍为完整响应，MCP 可显式 compact=false。完整任务包复用 start/read 的结果，缺失时用 phase_team_read(request_role=...) 获取。磁盘事件、历史和审核记忆不删除。
- 保留显式 consult=[]、单角色、双角色，及未指定时双角色的兼容默认；协调者按问题选择，没有关键词分类器或代码自动选择科学路线。工作流说明要求尽量使用新子上下文、只传独立任务包；客户端能力不能由 Python 代码保证，本次没有派生子 Agent。
- 复用 timed_call 为原生来源校验、索引、控制上下文和证据派生记时。未增加并行调度、异步科学写入、取消即零执行的语义或副作用自动重试。

## 基线与测量方法

基线是本任务开始时的磁盘工作树，不是 Git HEAD。仅四个相关模块副本保存在受控 TemporaryDirectory 中，按原模块名载入隔离 worker，保证旧代码的延迟导入也使用对应旧模块：

| 模块 | 修改前 SHA256 |
| --- | --- |
| evidence/snapshot.py | 9e13d6e60fa269cc225f5a0fb5fda2834b6fb09f0bb8aa9d195e4e56cadc2bef |
| models/transport_tables.py | 856b8e3073141b739c326600b7bd812ba15d005335a48c49ca0138d9dd385fd2 |
| agents/strategic/codex_team.py | 1728f43dbf793a5ad01485baf21bf8e93c77277e41e5fe03a27b1e4c96e4dc90 |
| evidence/decision_evidence.py | b5d444899880f32137927980f5f520d9b5c267b85a5d97f864d481b294a11332 |

py1，psutil 5.9.0，BLAS/OMP/MKL 线程统一为 1；最终对照 worker 固定在同一允许逻辑 CPU。父进程给每个自有 worker 设置 Windows Job 1536 MiB 提交内存硬限制和 150–240 秒超时，按 5 ms 采样 RSS/private；超时只终止该验证子进程。最初 1024 MiB 导入试验触发 MemoryError，不能当成项目泄漏证据。校准期一次较大长测触发超时；失败现场也由父临时目录清理。

合成状态逐步为约 1.4、11.4、45.5、90.9 MiB，含任务、嵌套诊断数值、只用于历史审计的大字段、候选和版本。各 worker 的科学数据形状/数值相同，使用各自临时目录及讨论身份；不强行把跨目录的项目/团队身份伪装相同。固定输入回归另外验证快照哈希与旧编码逐字节一致；同一 worker 重复读的 snapshot_id 必须不变。

墙钟用 perf_counter，CPU 用 process_time。每次操作前 GC 并记录进程基线；结束时释放响应和编码、GC 后记录结束 RSS/private。每次请求的峰值为父进程采样最大值；同时记录 Windows 自进程启动以来的内核工作集峰值（包括初始化），二者不混用。没有用 tracemalloc 代替进程内存。父进程不接收科学状态正文，只接收身份、计数、字节和耗时。

阶段时间为包含式计时，不把嵌套项直接相加。索引字段延迟解析单独记录；source_io 统计源文件 read 返回的字节，包括缓存命中、重复哈希和完整索引校验，不是物理磁盘设备流量。输入字节为实际 state.json 大小。普通业务响应使用紧凑、排序 JSON UTF-8；MCP 编码项复用实际文本内容和 JSON-RPC 外层格式，不启动真实 stdio 服务或发送完整数据到客户端。模型调用为 0；真实原生客户端/模型等待不可观测，记为未知，不算本地计算耗时，也不报告 token。

cold start 包含首次上下文/相关库预热，不等于 CodexOffline 的完整真实项目初始化。本基准使用真实 LocalAgentControl 和 CodexTeam，handler 为合成项目；真实台账加载、模型运行时和客户端聊天内存未测。

明确的计数变化：有有效索引时，完整 JSON 读取/解析在 start 从 2 次降为 0 次、暖读从 1 次降为 0 次；仍有两次完整强来源哈希和一次完整索引内容核验。advise 快照从 2 次降为 1 次，草案/Simulation 同类重复也由回归限制为 1 次。正常读仍需重建一次当前证据和快照，没有跨请求复用陈旧事实。

源读取总字节可能增加：索引不是跳过强校验的捷径；收益来自不把无关历史解析、保留为 Python 对象，以及减少中间表示。不能把“0 次完整 JSON 解析”写成“不读取状态”。

12 次重复读取中，优化后结束工作集在较窄范围波动；基线也逐渐接近平台。此结果支持瞬时峰值和分配高水位的改善，不能证明或排除更长运行、真实项目或客户端的泄漏。大样本基线存在明显墙钟/CPU 波动，保留读数及超时，不给出可外推的单一倍数。
